# System Architecture Diagram

:::caution As-built, not the original plan
The Milestone 1 System Architecture document described a cloud-network topology running inside an
OpenShift/Kubernetes cluster — with an Auth/JWT service, a GeoJSON API, a Risk Calculator
microservice, an Alert Engine, a Tile Server, and an Export API. **None of that infrastructure exists
in any of the three EOHA repositories today.** There are no Kubernetes manifests, no Dockerfiles, no
auth code, and no alerting code anywhere in `eo-datapipeline`, `eoha_backend`, or `eoha-prototype`.
This page has been rewritten to describe the system as it actually runs. The original PDF is linked
at the bottom for historical/planning reference.
:::

---

## As-built component diagram

```text
┌────────────────────────────────────────────────────────────────────┐
│  GitHub Actions (eo-datapipeline repo)                              │
│  cron: '0 0 1 * *' (monthly) + manual workflow_dispatch             │
│                                                                       │
│      python etl_pipeline.py                                         │
│         │                                                            │
│         ├─→ Google Earth Engine (MODIS, ERA5-Land, WorldPop,        │
│         │    ESA WorldCover) — batch export per province             │
│         │                                                            │
│         ├─→ Google Cloud Storage (CSV staging, per province)        │
│         │                                                            │
│         └─→ PostgreSQL on AWS RDS                                   │
│              upsert into: zone, malaria_observation                 │
└──────────────────────────────┬────────────────────────────────────┘
                               │  (same database, read-only)
┌──────────────────────────────▼────────────────────────────────────┐
│  eoha_backend  (Spring Boot 4, Java 21)                             │
│  GET /api/zones/*, GET /api/malaria-observations/*                  │
│  No authentication. No known caller.                                 │
└───────────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────┐
│  eoha-prototype  (static HTML/CSS/JS, no bundler)                   │
│  Reads data/Limpopo_Risk_Jan25_Jan26_Safe.csv, bundled in-repo       │
│  calculateDynamicRisk() — fixed rule-based scoring, runs in browser │
│  No HTTP call to eoha_backend or eo-datapipeline anywhere.           │
│  Live at an AWS Amplify URL; the deploy hookup is not in this repo   │
│  (tracked CI only runs a file-existence check + Discord notify)      │
└───────────────────────────────────────────────────────────────────┘
```

The top block and the bottom block are **not connected**. This is the single most important
correction to the original diagram: it drew one continuous pipeline from satellite ingestion to
dashboard rendering. In reality, the dashboard's data was placed in its repo by some out-of-band
process and is not regenerated by the pipeline above.

## Component reference

### `eo-datapipeline` — data ingestion

| Property | As-built value |
|---|---|
| Trigger | GitHub Actions `schedule: cron` + `workflow_dispatch` — not a Kubernetes CronJob |
| Runtime | `ubuntu-latest` GitHub-hosted runner, Python 3.11.9 — no container |
| External calls | Google Earth Engine (batch export), Google Cloud Storage, PostgreSQL |
| Idempotency | All writes are `INSERT ... ON CONFLICT DO UPDATE` |

Full detail: [`eo-datapipeline/SUMMARY.md`](https://github.com/MEDICONSORTIUM/eo-datapipeline/blob/main/SUMMARY.md).

### `eoha_backend` — REST API

| Property | As-built value |
|---|---|
| Framework | Spring Boot 4.1.0, Java 21, layered Controller→Service→Repository |
| Endpoints | 11 total — 2 health checks, 4 zone reads, 5 observation reads, all `GET` |
| Auth | None |
| Known consumers | None found in either sibling repo |

Full detail: [`eoha_backend/SUMMARY.md`](https://github.com/MEDICONSORTIUM/eoha_backend/blob/main/SUMMARY.md).

### `eoha-prototype` — dashboard

| Property | As-built value |
|---|---|
| Structure | Static multi-page HTML, vanilla JS, CDN-loaded Leaflet/Chart.js/PapaParse — no framework, no bundler |
| Data source | A CSV file bundled directly in the repo (`data/`) |
| Risk scoring | Client-side `calculateDynamicRisk()` — a fixed rule-based formula, not a model |
| Hosting | Claimed to be AWS Amplify; the tracked `deploy.yml` workflow does not perform a deploy — it only checks `index.html` exists and posts a Discord message |
| Tests | Zero currently run — a prior Playwright suite was removed from the repo (recoverable from git history) |

Full detail: [`eoha-prototype/SUMMARY.md`](https://github.com/MEDICONSORTIUM/eoha-prototype/blob/main/SUMMARY.md).

## What the original diagram described that doesn't exist

For traceability, every zone/service in the original Milestone 1 diagram and its current status:

| Original zone/service | Status |
|---|---|
| OpenShift/Kubernetes cluster | ❌ Not present — no manifests, no Helm charts, no container orchestration in any repo |
| Auth / JWT (session management) | ❌ Not present — no authentication code anywhere |
| GeoJSON API (ward boundary service) | ❌ Not present — `eoha-prototype` fetches static `.geojson` files directly, not through an API |
| Risk Calculator (server-side microservice) | ❌ Not present — risk scoring runs client-side only, in `eoha-prototype`'s JS |
| Alert Engine | ❌ Not present — no thresholds, no notification code, no Alert Store |
| Tile Server | ❌ Not present — `eoha-prototype` loads CartoDB/OpenStreetMap tiles directly from their public CDNs |
| Export API (PDF/CSV/PNG) | ❌ Not present — the Reports page exports CSV client-side via the browser's Blob API only |
| Scheduler (Kubernetes CronJob) → GEE Sync | ✅ Exists, but as a GitHub Actions cron job, not a Kubernetes CronJob |
| EO Pipeline / Data Ingestion / Ward Scoring | ✅ Exists — this is `eo-datapipeline`'s `etl_pipeline.py` |
| Ward Risk CSV data store | ⚠️ Exists as a static file bundled in `eoha-prototype`, not as a store the pipeline writes to |
| GEE Image DB | ✅ Exists implicitly — GEE itself is queried live each run; nothing is separately cached |
| AWS Amplify / GitHub Actions (hosting/CI) | ⚠️ Partially — GitHub Actions exists for both repos' CI, but the frontend's actual Amplify deploy hookup is not visible in-repo |
| Audit Log | ❌ Not present |
